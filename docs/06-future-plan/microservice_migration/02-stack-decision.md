# Stack Decision

## Decision Summary

The recommended stack is a **modular monolith backend + two frontend apps**.
This is the best fit for the current project size and product scope.

## Recommended Stack

### Frontend

- `Next.js`
- `TypeScript`
- `Tailwind CSS v4`
- `shadcn/ui`

### Backend

- `Python 3`
- `FastAPI`
- `Pydantic` for request, response and configuration validation
- `pytest` for backend tests
- `OpenAPI` generated by FastAPI as the API contract source

The FastAPI application is deployed as a separate Vercel project from
`services/api`. Next.js Route Handlers, NestJS and Fastify are not used for the
main business API in the first implementation.

### Data

- `Supabase PostgreSQL`
- `Google Drive` for media files
- `ImageCache` table for mapping image path to Drive URL

### Shared Layer

- OpenAPI specification generated by FastAPI
- generated TypeScript API client for Web and Admin
- shared frontend constants and TypeScript configuration
- API error and pagination contracts defined by the backend

Python models remain authoritative for backend validation. Frontend types are
generated from OpenAPI instead of manually duplicating Pydantic models in Zod.

### Repository Tooling

- `npm workspaces` manage the root Public Web, Admin Portal and TypeScript
  packages.
- Python dependencies are managed independently in `services/api`.
- Keep the existing `package-lock.json` during the foundation phase.
- Turborepo is deferred until the build graph requires it.

## Why Not Full Microservice Split Yet

- The project still has one dominant domain.
- Team/process overhead would grow faster than product value.
- Separate services would add deployment and observability work too early.
- The admin portal only needs a clean boundary, not many independently scaled services.

## Why Keep Google Drive

- already aligned with the current document flow
- lower migration risk
- keeps image handling stable during the backend refactor
- avoids changing both storage and app architecture at the same time

## Stack Rules

- Do not let public UI read Supabase directly.
- Do not let admin UI write to DB directly.
- Keep backend as the only integration point for data and media resolution.
- Avoid introducing a message queue until there is a real async use case.
